  ---
  AXI GPIO v2.0 dual-channel output write-latching bug

  Symptom. xilinx.com:ip:axi_gpio:2.0 configured with C_IS_DUAL=1 and both channels as C_ALL_OUTPUTS{,_2}=1 silently drops AXI writes to the second channel's GPIO2_DATA register (offset
  +0x08). Writes return BRESP=OKAY; subsequent reads of the same register return 0x00000000; gpio2_io_o[*] outputs stay at synthesised default. Channel 1 (+0x00) works correctly under
  identical configuration. Confirmed on Vivado 2024.1, target xck26-sfvc784-2LV-c (KR260 SoM), xilinx.com:ip:axi_gpio:2.0.

  Synthesis fingerprint. The IP's OOC synth log emits, for every bit of the channel-2 width:
  WARNING: [Synth 8-6014] Unused sequential element
    Dual.ALLOUT1_ND_G2.READ_REG2_GEN[<i>].GPIO2_DBus_i_reg was removed.
    [.../axi_gpio_v2_0_vh_rfs.vhd:790]
  A symmetric set fires for channel 1 (Dual.ALLOUT0_ND_G1.READ_REG_GEN[*].GPIO_DBus_i_reg, vhd:693) but ch1 still works at runtime — the two Dual.ALLOUT*_ND_G* branches don't degrade
  equivalently.

  Verified via direct hardware test on KR260:
  - wr 0xa0000000 0x3 → rd 0x3 ✓ (ch1 latches)
  - wr 0xa0000008 0xdeadbeef → rd 0x0 ✗ (ch2 writes vanish)
  - Downstream consumer (my_state 64-bit accumulator wired to gpio2_io_o[31:0]) never observes a non-zero addend.
  - All other diagnostics pass: app Active, fpga_manager operating, both UIOs map at expected addresses, no other /proc/iomem claimant, axi_pmon UIOs and ch1 of the same IP work.

  Workaround we are applying. Replace the dual IP with two separate axi_gpio:2.0 instances, each C_IS_DUAL=0. The single-channel synthesis path doesn't enter the Dual.* generate hierarchy,
   so the trimming heuristic is never invoked. Cost is ~one extra IP's worth of AXI-Lite plumbing plus an additional MI port on the interconnect.

  Things we did NOT try (worth checking the forum for):
  - KEEP_HIERARCHY / KEEP / DONT_TOUCH synthesis attributes on the IP cell
  - Non-default IP synth strategy (e.g., MAX_FANOUT low, register replication off)
  - Older axi_gpio:1.01 revisions (different generate structure, may predate the bug)
  - Adaptive Computing / Xilinx Answer Records search (e.g. AR# entries, ChipScope tracing of the AXI handshake)
  - Asymmetric channel widths (e.g. ch2=32 vs. ch2=8) to see if the trim threshold is width-dependent

  Useful search strings:
  - Dual.ALLOUT1_ND_G2.READ_REG2_GEN GPIO2_DBus_i_reg removed
  - Synth 8-6014 axi_gpio_v2_0_vh_rfs.vhd 790
  - axi_gpio dual channel write not latching Vivado 2024.1
  - C_IS_DUAL C_ALL_OUTPUTS_2 GPIO2_DATA register optimised away
